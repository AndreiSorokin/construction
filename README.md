## ⭐ Гонка refresh-токенов (две вкладки / `target=_blank`) — как решено

Проблема: при **ротации** refresh-токенов токен одноразовый. Если две вкладки одновременно
обнаружат, что access протух, и обе дернут `/auth/refresh` с одним и тем же refresh —
первая ротирует его, вторая придёт уже с «погашенным» токеном, сервер сочтёт это
переиспользованием и разлогинит сессию. Решение сделано **на двух уровнях**.

**Сервер — ротация с атомарным захватом + grace-окно** (`server/src/auth/token.service.ts`):
- refresh-токен = `"<id>.<secret>"`, в httpOnly-cookie; в БД хранится `sha256(secret)`.
  Токены объединены в «семью» (`familyId` = одна сессия устройства).
- При обмене ротацию **атомарно захватывает один запрос**:
  `updateMany({ where: { id, rotatedAt: null }, data: { rotatedAt: now } })` — выигрывает ровно один.
- Проигравшие в пределах **grace-окна (20 c)** считаются легитимной гонкой вкладок и получают
  валидную новую пару в той же семье — **без разлогина**.
- Переиспользование токена **вне окна** или уже отозванного → трактуется как компрометация →
  **отзыв всей семьи** (`revokeFamily`). Это стандартная reuse-detection.

**Клиент — single-flight в три слоя** (`client/lib/auth/refresh-client.ts`):
1. В рамках вкладки — общий promise (`inflight`): параллельные вызовы ждут один запрос.
2. Между вкладками — **Web Locks API** (`navigator.locks.request`): refresh выполняет ровно одна
   вкладка; остальные, зайдя под лок, видят уже свежий токен и в сеть не идут.
3. **BroadcastChannel**: выигравшая вкладка рассылает новый access-токен остальным.

Access-токен живёт только в памяти; refresh — в httpOnly-cookie (JS его не читает, XSS-safe),
уходит автоматически с `credentials: 'include'`. Итог: даже при множестве вкладок и `target=_blank`
обновление токена не ломается.

## Авторизация — кратко
- `POST /api/auth/login` `{login,password}` → `{accessToken, user}` + ставит httpOnly-cookie `refresh_token`.
- `POST /api/auth/refresh` (по cookie) → новый `{accessToken}` + ротация cookie.
- `POST /api/auth/logout` → отзыв семьи + очистка cookie.
- `GET /api/auth/me` — профиль (по Bearer access-токену).
- Глобальный `JwtAuthGuard`; публичные ручки помечены `@Public()`. Роли — `@Roles(Role.ADMIN, …)` + `RolesGuard`.

## Что готово и что достраивается
**Функционал — полный.** API: auth (JWT + ротация refresh с защитой от гонки), заявки (7 типов:
создание → маршрут согласования → отметки склада по позициям → снабжение: взять/назначить/стадии/
отложить/заметки → выполнено → подтверждение/возврат), наряды (период, ИП с признаком НДС, работы из
прейскуранта, маршрут, суммы и ДСУ), вложения (S3, multer, presigned), блокнот, письма-уведомления
согласующим (nodemailer), и всё администрирование: люди, отделы, объекты с доступами, номенклатура,
ИП, справочники работ (CRUD + импорт JSON/CSV + экспорт), маршруты (3 отдела × 7 типов + наряды).

UI (Next.js, App Router): вход, доска снабжения по стадиям, списки/фильтры/поиск, карточки заявки и
наряда со всеми действиями по ролям, формы создания (динамические поля по типу; подбор работ с
поиском и счётчиками), блокнот, настройки, печатные формы заявки и наряда, бейджи «на согласовании
у меня», мобильная навигация, фоновое обновление списков каждые 30 с.

Seed: орг.структура, все маршруты, **полные прейскуранты 118 + 116 работ**, номенклатура, ИП.
Демо-документов нет — база чистая для реальной работы.
